# The library as a game component

Where `crystal-battle` is going: a library Rustic Crystal and Rustic Yellow
drive a whole battle with. The game hands it everything it knows (its
parties, its player, its bag, its game data), pumps events while the player
and the AI decide, and gets the battle's result back to write into its save.
The battle still plays exactly like the original's (see [goal.md](goal.md)):
the same random draws, the same messages in the same order, the same result.

**Status:** done on branch `library-io` (steps 1–6 below), each step landed
with the differential testers green.

## Principles

- **No ROM.** The library builds without `pokecrystal.gbc`. Game data is typed
  Rust (`GameData`), generated once from a built ROM and its `.sym` file by
  `tools/gen_game_data.py`; the engine never addresses ROM bytes. The harness
  keeps the ROM: the transpiled original needs it.
- **The game's data is a value, not a feature.** `GameData::crystal()` is
  built in. Another game built from a pokecrystal fork (Crystal Legacy) is
  another `GameData`, generated by the same script; differences in *code*
  (rules) become a small `Rules` value passed with it. Cargo features only
  decide which built-in data sets are compiled in.
- **Strings are opaque.** Names are plain `String`s the caller passes in
  (nicknames, the player, the rival, trainer names) or that `GameData` holds
  (species, moves, items). The library never renders or inspects text; no
  battle logic depends on a name (traded-ness is the OT *ID*). Glitch text
  (Beat Up's garbage names past the party, `<MOBILE>` scripts) is out of
  scope.
- **Typed messages, not text.** The engine decides which message appears and
  when (that is battle logic and stays exact), and emits it as a
  `battle::Message`: one variant per battle text, with typed fields (sides,
  names, moves, items, numbers). The game renders it with its own text engine.
  A renderer for Crystal's exact English lives in the harness, where the
  differential tester checks the message stream against the original's
  captured text.
- **Every visible effect is an event.** Besides messages and HP bars: move
  and battle animations, cries, sound effects, send-outs, withdrawals, faints,
  substitutes, transforms, status and stat-stage changes, the experience bar,
  level-ups, ball shakes. The engine emits each where the original plays it
  (with its Battle Scene option), and the harness hooks the original's
  animation/sound routines to verify the stream.
- **Exactness of out-of-range reads.** The original sometimes reads a table
  past its end (move 0, move `$ff`, species 0). Typed tables cover the whole
  `u8` index range; the entries past the real data hold what the original
  reads there, decoded at generation time.

## Shape of the API

```rust
use crystal_battle::battle::*;
use crystal_battle::data::GameData;

let setup = BattleSetup {
    player: Player { name, id, gender, money, johto_badges, kanto_badges, mom_saving, mom_money },
    party: vec![Pokemon { .. }],      // every field of the save's party_struct, nickname, OT name
    bag: Bag { items, balls },        // (item, quantity) per pocket
    opponent: Opponent::Trainer { class, id, party: None, items: None, ai_flags: None, control },
    //     or Opponent::Wild { species, level }, Opponent::Link { name, party }
    options: Options { battle_scene: true },
    world: World { time_of_day, unlocked_unowns, rival_name, seen, caught, unown_dex },
};
let mut battle = Battle::start(GameData::crystal(), &setup, seed)?;
loop {
    for event in battle.events() { /* Message, HpBar, … */ }
    match battle.status() {
        Status::Decision(d) => { battle.step(choose(d))?; }
        Status::Ended { .. } => break,
    }
}
let result: BattleResult = battle.result().unwrap();
// party (HP, PP, status, exp, levels, moves; a caught mon), money, Mom's
// money, Pay Day money, the bag, the slots that may evolve, the Pokédex
```

`BattleResult` gives back the same `Pokemon` type the setup took in, so a
game can write the party straight back into its save. The scenario type
`BattleConfig` (species + level, the TOML schema) stays as a convenience:
`BattleSetup::from_config(&config, seed)` makes the setup the way the game
makes new mons, and the random stream after it; `Battle::start` from those
plays exactly the scenario's battle (`examples/setup_diff` checks every
decision, the battle memory at each, the outcome and the result).

## Steps

1. ✅ **Typed `GameData`.** Generate species, moves, items, trainers, type chart,
   effect scripts and the small mechanic tables; replace every ROM read in
   the engine with a typed lookup. Verified by `engine_diff` /
   `engine_fixtures` after each table.
2. ✅ **`Message` events.** One variant per battle text; the engine emits them
   instead of rendering ROM text. The harness renderer reproduces Crystal's
   English; the testers compare it with the original's captured text. Names
   leave the engine's memory model (the testers stop comparing name
   buffers).
3. ✅ **`BattleSetup` input.** Full parties, player, bag, world state; the engine
   seeds its state from them. `BattleConfig` converts to a `BattleSetup`.
4. ✅ **`BattleResult` output.**
5. ✅ **Presentation events**, verified against hooks on the original's
   animation and sound routines: `Event::Animation`, `Sound`, `Cry`,
   `Faint`, `SlideOut`, `TrainerSlidesIn`, `ExpBar`, `StatsBox`,
   `Frontpic`, `BallWobbles`.
6. ✅ **ROM-free build**: the library has no ROM; the text renderer, the
   ROM image and the ROM-patch helpers live in the harness. The map
   location a battle reads (`World::location`) is an input; a read of the
   game's code (Beat Up past the party, wrapping to ROM bank 0) is an
   unsupported glitch.

## Crystal Legacy

`GameData::crystal_legacy()` (cargo feature `crystal-legacy`) is
[Crystal Legacy](https://github.com/cRz-Shadows/Pokemon_Crystal_Legacy)
V1.3.1's data: its base stats, learnsets, evolutions, TM/HM sets, moves,
items and tables, generated by `tools/gen_game_data.py --game crystal-legacy`
from a build of the V1.3.1 tag (identical to the official patch on Crystal
1.0). What a fork changes that the ROM and its `.sym` don't say (the TM item
layout, the trainer party format) is a profile in the generator.

- **Parties.** Legacy's trainer party format (nicknames, DVs, stat
  experience, happiness, stages picked by badge count) isn't decoded:
  `GameData::trainer_parties` is empty, so a trainer battle brings its own
  party, and one against a built-in trainer is `StartError::Unsupported`.
- **Base PP.** What depends on a move's base PP outside the engine's memory
  (the legal PP items, a scenario's moves) reads the game's data
  (`ReadMem::base_pp`), not Crystal's table.
- **Scenarios.** `BattleSetup::from_config_in(data, …)` makes a scenario's
  mons from another game's data.
- **Rules.** Legacy also changes the battle's code (Ghost moves special and
  Dark moves physical, fixes to known bugs, AI fixes). Those aren't ported
  yet: on Legacy's data the engine still plays by Crystal's code.

Later: the engine's state is still the original's WRAM byte for byte
(`engine::mem::Mem`). Replacing it with typed state, routine by routine, is
the step after this one; the testers will then compare a typed projection of
the state instead of raw memory.
