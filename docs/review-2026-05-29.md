# Review of lu-cli-actions: ab00fad..HEAD

Audited four commits: `bf39a35`, `756fb89`, `9b27fac`, `f6d8052`.
Verified `cargo build` and `cargo test` (24 passed) at HEAD. Verified the
recording / playback / `--random` flows end-to-end on `scratch/cli.toml` and
on a generated random battle.

## Verdict

GREEN. No correctness or stability blockers in the four commits. A handful
of nits, one cross-cutting pre-existing bug exposed by the recording
workflow, and a documentation/code drift around `--random` items.

## Per-commit notes

### bf39a35 — Zero stale move ids on offer_switch Accept

- The patch matches the asm contract precisely. Cross-checked
  [`scratch/pokecrystal/engine/battle/core.asm:3488-3515`](../scratch/pokecrystal/engine/battle/core.asm):
  the Accept exit writes `wLastPlayerMon`, `wCurBattleMon`, **restores**
  `wCurPartyMon` (push/pop), and zeros `wCurEnemyMove`/`wCurPlayerMove`
  before returning with `flag_c = 0`. Our patch at
  [`src/game/engine/battle/core.rs:14570-14582`](../src/game/engine/battle/core.rs)
  writes the same four bytes (move ids added in this commit) and
  intentionally leaves `wCurPartyMon` alone — equivalent to the asm's
  push/pop restore since nothing in our `handle_offer_switch` path mutates
  it. The Keep path correctly sets `flag_c = true` only.
- The skipped UI calls (`ClearPalettes` / `DelayFrame` / `_LoadHPBar`) are
  the same ones we already skip in the action-menu Switch path — the
  rationale is documented inline and in
  [`docs/transpiled_code.md`](transpiled_code.md). Consistent with the
  existing harness convention.
- Trapping: the Accept path doesn't need to consider `wPlayerWrapCount` /
  `SUBSTATUS_CANT_RUN` here — the asm doesn't either; `offer_switch` only
  fires when the enemy is sending in a fresh mon, which doesn't trigger
  during a Wrap/Mean Look lock on the player. The action-menu Switch path
  enforces trapping via `check_can_switch`. ✓
- Patch markup is conventional and the
  [`docs/transpiled_code.md`](transpiled_code.md) table row was updated.
- The three other switch paths (action-menu Switch, forced switch after
  faint, offer_switch Keep) were re-examined and look correct against
  `TryPlayerSwitch` (asm 5150-5188) and `force_pick_party_mon_in_battle`
  (asm not shown but mirrored by the existing patch at
  [`src/game/engine/battle/core.rs:12107-12122`](../src/game/engine/battle/core.rs)).

### 756fb89 — Record CLI battles to a TOML action script

- Recording lives in `cpu.recorder = Option<RefCell<BufWriter<File>>>`
  ([`src/runtime/cpu.rs:37-46`](../src/runtime/cpu.rs)). The `RefCell` is
  fine: the Cpu only ever runs on `cpu_thread`, so `Send` (not `Sync`) is
  the only bound that matters. No threading concerns.
- The recorder is installed only after `resolve_seed` runs in `run_with`
  ([`src/bootstrap/mod.rs:377-383`](../src/bootstrap/mod.rs)) — the
  resolved seed always lands in the header, even when the scenario omits
  `seed = ...`. Verified empirically.
- Each `Step` is `writeln!`-then-`flush()`. A mid-battle crash leaves a
  valid TOML prefix on disk — verified by killing the process partway
  through a battle and re-parsing the file with `toml`.
- The hand-rolled TOML writer escapes `"`, `\\`, `\n`, `\r`, `\t` in path
  strings — paths the user is realistically going to pass are safe. A
  control character in the path would survive as literal in `to_string_lossy`
  but `toml_string` doesn't escape arbitrary control chars (e.g. NUL,
  0x7F). Strict TOML rejects raw control characters in basic strings —
  borderline failure mode, irrelevant in practice. Nit only.
- The `Step::Move` variant is reused both for the action-menu Move *and*
  for `move_selection_screen` re-pick (Disable / No-PP). Inline comment
  in
  [`src/bootstrap/cli.rs:189-193`](../src/bootstrap/cli.rs) explains the
  choice; replay then disambiguates by prompt site, not step kind. Works,
  but means a re-pick step is indistinguishable in the recording from a
  regular Move on inspection. Nit.
- The argv parser is hand-rolled; it correctly errors on missing
  `--record <path>` operand and unknown flags. Order-insensitive between
  the positional and `--record`.
- Test `header_and_steps_round_trip_through_toml_parser` covers every
  step kind including both arms of `OfferSwitch` and both arms of `Item
  target`. Good coverage.

### 9b27fac — Play back recorded CLI battles via --play

- Drift detection works. Reproduced the underflow case (truncated
  recording → exit 2 with "ran out of steps at decision #N
  (<site>)" — confirms message includes the 1-based step index and the
  prompt-site label). Reproduced the kind-mismatch case (hand-edited
  `kind = "move"` → `kind = "forced_switch"` at step 1 of a recording →
  exit 2 with the recorded kind, the expected list, and the prompt site).
- The recording's seed *always* wins (`seed_override` in
  [`src/bootstrap/mod.rs:368-374`](../src/bootstrap/mod.rs)). Verified
  with a scenario `seed = 0xc0ffee` + a recording header
  `seed = "0xdeadbeef"`: the stderr "battle: using seed
  0x000000000deadbeef from recording" fires, no ambiguity. Matches the
  docs.
- Record + play coexist. Re-recording a replay produces a bit-identical
  output file (compared with `diff` after replaying the result twice).
  The "re-record from recording" path also re-records the playback step
  at `handle_move_selection` / `handle_forced_switch` /
  `handle_offer_switch` — covered with explicit inline comments. ✓
- One UX inconsistency, not a correctness bug: in playback mode the
  `print_battle_state` call inside `handle_offer_switch` /
  `handle_forced_switch` is skipped (the early `consume(...)` return
  short-circuits the print). In live mode the prints happen. So the
  stderr stream during a replay shows one fewer state block per
  offer_switch / forced_switch event than the original record run.
  Battle state itself is identical; only the trace differs.
- Edge case I verified: passing `--play x.toml my_scenario.toml` when
  `x.toml` already carries `source_scenario` — the positional wins
  silently (no warning). The docs say this is intentional ("useful for
  re-running the same script against an edited scenario") so OK. The
  `--play` of a `source_scenario = "random"` recording with a positional
  scenario.toml *silently drops* the positional and regenerates from the
  seed (see [`src/main.rs:50-59`](../src/main.rs)). Worth an explicit
  error or warning. Nit.
- Edge case I verified: `--play <recording-with-missing-source>` →
  `bootstrap::load_battle` reports `could not read battle file: No such
  file or directory`. Clear enough but the path the user passed isn't in
  the message because `load_battle`'s error doesn't include the path.
  Pre-existing.
- Test `load_matches_recorder_output` does a real round-trip through
  recorder + parser. `unknown_kind_errors` covers the parser's reject
  path. `seed_decimal_and_hex_both_parse` covers seed shape. No test
  for the kind-mismatch and underflow paths (they `std::process::exit(2)`
  so they're hard to test in-process), but I exercised both manually.

### f6d8052 — Add --random for seedable randomized trainer battles

- Same seed → same matchup *and* same battle outcome. Verified with two
  `--random --seed 0xdeadbeef --record /tmp/{a,b}.toml` runs piped the
  same input; the two recordings are byte-identical (`diff /tmp/a.toml
  /tmp/b.toml` prints nothing). Trainer, party (species + levels), and
  bag entries match. The pre-battle eprintln of "random battle: seed
  0x... — vs <trainer> — ..." also matches. ✓
- `--random` → record → `--play` round-trip works: replaying the
  recording regenerates the scenario from `source_scenario = "random"` +
  the recorded seed and proceeds bit-identically. Verified that the
  battle state lines (`=== Enemy:` / `=== You:`) match between the
  original run and the replay for every shared turn.
- Argv mutual exclusion errors all fire correctly:
  - `--random scratch/foo.toml` → "--random cannot be combined with a
    scenario path"
  - `--random --play x.toml` → "--random cannot be combined with --play
    — use `--play <recording.toml>` alone..."
  - `--seed 1 --play x.toml` → "--seed cannot be combined with --play —
    playback always uses the recording's seed"
  - `--seed 1` (no `--random`) → "--seed without --random has no effect"
  - `--seed not-a-number` → "could not parse \"not-a-number\""
  - `--seed 0xdeadbeef` and `--seed 42` both parse.
- Bounds I checked in
  [`src/bootstrap/random.rs:36-58`](../src/bootstrap/random.rs):
  - Level delta = `ceil(avg/10)`, clamped `≥ 1`. For Falkner (avg 8)
    that's ±1 → levels 7..=9. For Red (avg 77) → ±8, clamped to 100.
  - Party count = `party_count ± 1`, clamped to `1..=6`. Lance
    (party_count 6) → 5..=6. Bugsy (3) → 2..=4. No off-by-one.
  - `rng.in_range(lo, hi)` is `lo + below(hi-lo+1)` so `lo == hi` is safe
    (no `% 0`).
  - `BATTLE_ITEMS.len() > 0` so `below(len)` is safe.
- Species pick is uniform over the 251 Gen-1+Gen-2 dex
  ([`src/bootstrap/species.rs`](../src/bootstrap/species.rs)). No
  egg/missingno/Unown-form slot, so all picks are valid `try_add_mon_to_party`
  input. ✓
- `BATTLE_ITEMS` test (`battle_items_all_resolve`) verifies each name
  resolves through `items::lookup`. Good. But: the list includes
  `Ether`, `Max Ether`, `Elixer`, `Max Elixer`, `X Attack`, `X Defend`,
  `X Speed`, `X Special`, `X Accuracy`, `Dire Hit`, `Guard Spec` — none
  of these IDs are in `item_supported` in
  [`src/bootstrap/cli.rs:430-440`](../src/bootstrap/cli.rs), so they
  appear in the bag but never show up as a Use option in the CLI menu.
  The docs in [`toml_schema.md:73`](toml_schema.md) claim the list
  includes "X-items", which is misleading. This is a *correctness gap
  between code and docs*, not a bug — the items just become unusable bag
  weight. See Recommendations.
- The generator and the engine RNG both use the same `u64` seed (the
  generator pins it into `BattleHeader.seed`). Verified that
  `random_battle_config(seed).battle.seed == Some(seed)` so a single
  `--random --seed N` run is reproducible end-to-end. ✓
- Duplicate item IDs are possible (e.g. "X Attack x1" twice in a
  generated bag). `seed_player_items` doesn't merge them; they go into
  separate bag slots. The engine's bag normally has unique IDs per slot.
  `decrement_pocket_item` in
  [`src/bootstrap/cli.rs:522-551`](../src/bootstrap/cli.rs) finds the
  first matching slot and decrements/removes it, leaving the second slot
  intact. Functionally OK; cosmetically odd. Nit.
- `random_entropy_seed` in [`src/main.rs:359-370`](../src/main.rs) is a
  near-verbatim copy of `system_entropy_seed` in
  [`src/bootstrap/mod.rs:417-428`](../src/bootstrap/mod.rs). The
  duplication is small but unnecessary; either could call the other.
  Nit.

## Cross-cutting concerns

- **HARNESS-PATCH discipline is intact.** `rg HARNESS-PATCH src/` lists
  the same 13 patch sites as before; the only diff in
  [`docs/transpiled_code.md`](transpiled_code.md) is the offer_switch
  row update from bf39a35. No new patches were added by 756fb89,
  9b27fac, or f6d8052 — those features sit entirely in
  `src/bootstrap/{recorder,player,random}.rs` + `src/main.rs` +
  `src/runtime/cpu.rs`. Clean separation.
- **Threading**:
  [`src/main.rs:175`](../src/main.rs) still uses
  `recv_timeout(Duration::from_millis(16))`, so the event loop continues
  to pump while the CPU thread can block on stdin. Not regressed.
- **prompt_index EOF loop (pre-existing, exposed by the recording
  workflow).**
  [`src/bootstrap/cli.rs:380-397`](../src/bootstrap/cli.rs)'s
  `prompt_index` treats `read_line(...).is_err()` as EOF, but stdin EOF
  returns `Ok(0)` (zero bytes), not Err. After a piped stdin runs out,
  the loop tight-spins printing "Enter a number 1..=N." to stderr until
  the process is killed. I hit this every time I ran a record session
  with `< /tmp/in.txt` — the recording itself was fine (the recorded
  steps for the supplied input came through clean) but the CPU thread
  never terminates. Not introduced by these commits (predates them in
  the same module) but the `--record` workflow makes it much more likely
  to bite a user / CI. Worth fixing alongside the recording work.
  Suggested fix: treat `Ok(0)` from `read_line` the same as Err.
- **Two entropy-seed helpers.** `system_entropy_seed` in
  `src/bootstrap/mod.rs` and `random_entropy_seed` in `src/main.rs` are
  duplicates. Consolidate.
- **Docs are well-aligned.** README's status list mentions all three new
  flags; `docs/toml_schema.md` has dedicated sections for `--record`,
  `--play`, and `--random`; mutual-exclusion table matches the
  implementation. The only doc/code drift is the X-items claim in
  `docs/toml_schema.md:73` (see Recommendations).
- **Test count.** 24 tests pass at HEAD, matching the brief.

## Recommendations (with severity: blocker / nice-to-have / nit)

1. **nice-to-have** — Fix
   [`src/bootstrap/cli.rs:385`](../src/bootstrap/cli.rs) `prompt_index`
   so an `Ok(0)` from `stdin().read_line(...)` is treated as EOF (the same
   path the existing `is_err()` branch takes). Without it, a piped-stdin
   record session tight-spins forever after input exhaustion. Pre-existing
   but the recording flow makes it user-visible.
2. **nice-to-have** — Reconcile `BATTLE_ITEMS` in
   [`src/bootstrap/random.rs:21-30`](../src/bootstrap/random.rs) with
   `item_supported` /
   [`apply_item`](../src/bootstrap/cli.rs) in `src/bootstrap/cli.rs`.
   Either drop the in-battle-unusable items (Ether/Max Ether/Elixer/Max
   Elixer/X-items/Dire Hit/Guard Spec) from `BATTLE_ITEMS`, or extend
   `item_supported` + `apply_item` to handle them. Today the docs claim
   X-items are picked; the CLI silently filters them out of the action
   menu.
3. **nice-to-have** — `--play <rec> <positional>` where `rec` has
   `source_scenario = "random"` silently drops the positional and
   regenerates. Either accept the positional as an override of the
   marker, or reject the combination with a clear error
   ([`src/main.rs:50-59`](../src/main.rs)).
4. **nit** — Consolidate the two entropy seed helpers (`random_entropy_seed`
   in `src/main.rs:359` and `system_entropy_seed` in
   `src/bootstrap/mod.rs:417`).
5. **nit** — The random generator can produce duplicate-ID bag entries
   (e.g. "X Attack" picked twice → two separate slots). Optionally merge
   on duplicate name in `random_battle_config` before constructing
   `ItemSpec`s.
6. **nit** — `Step::Move` is used both for the action-menu Move and the
   `move_selection_screen` re-pick path. Inspecting a recording can't tell
   them apart. Optional: a `kind = "move_repick"` variant for the
   Disable/No-PP path.
7. **nit** — Replay skips `print_battle_state` inside `handle_offer_switch`
   / `handle_forced_switch`. The battle is bit-identical but the stderr
   trace differs from the live run. Optional: print the same banner in the
   playback branch for stream-parity.
